# Part57 — Global signed Stripe follow-up backlog and safe original routing

## Application functionality

The finance panel now has `/admin/stripe-deposit-followups`: a current-account/current-checkout-configuration inbox, searchable by signed event ID/type, with arrival sorting, pagination, never-routed and last-unmatched filters. Staff no longer need to know the original deposit ID. There is no CRUD/create/edit/delete page, deposit selector, amount input, merchant/account override, provider URL input or arbitrary provider request.

A row's **Find original and inspect** action discovers candidate original deposits from the already authenticated signed event, then proves the selected original through the existing applied-capture/canonical-credit review boundary. Authorized **Routing history** displays redacted, authenticated historical routing summaries; raw encrypted provider payloads are not displayed. The existing deposit actions remain the place for full authorized review details and an exact-version acknowledgement note. An ID discovered by this queue is not a permission bypass for another resource.

**Route selected** accepts at most25 distinct positive integer inbox IDs. Each item has its own top-level SQL transaction. Expected financial/scope/proof refusals return individual `held` results; a successful earlier item remains committed. Revoked authorization and unexpected infrastructure faults abort the remaining batch; prior commits remain durable even if the UI only shows an interruption. Reopen the queue/history to inspect those earlier commits. The batch is deliberately NOT an all-or-nothing operation and does not silently truncate oversized selections.

## Activation and authority

Both `STRIPE_DEPOSIT_REVIEW_ENABLED=true` and the new `STRIPE_DEPOSIT_FOLLOWUP_ROUTING_ENABLED=true` are required. The new flag defaults OFF and is independent of original captured-funding credit activation. Retain the approved separate `STRIPE_DEPOSIT_FOLLOWUP_WEBHOOK_SECRET` and existing same-account API configuration required by Part56. Enabling the queue neither enables new credits nor creates a background worker.

Every service operation requires a current nondeleted active admin/super-admin with explicit `review stripe deposit followups` duty. Ordinary admins do not automatically receive this duty. Service checks use the existing primary-server current-staff boundary, not the supplied User model's cached role/status. Authority is checked before discovery, after ordered locks, by the coordinated review and before decision persistence. History also checks at entry and before returning. Existing panel access and current account/configuration filters apply to the resource query, not only navigation visibility.

Apply additive migration `2026_10_18_000400_create_stripe_followup_route_decisions.php` after Part56. Preserve the application encryption key and all original checkout/capture/inbox/review custody. The new table has restrictive inbox/deposit/staff foreign keys. It is appended through SQL domain coordination; the two new Eloquent models are read-only projections with sensitive receipt fields hidden. Their model save/delete events refuse writes. This is not a database-user restriction on every possible raw SQL writer.

## Discovery is a hint, never financial authority

Only the verified event object's top-level `reference`, `gateway_reference`, `payment_reference`, `id`, `payment_intent` and `charge` string facts can seed discovery. Only bounded `cs_`, `pi_` and `ch_` tokens are considered. Nested metadata, customer claims, deposit IDs, refund/dispute IDs, and expanded reference objects do not choose a wallet or target. Unsupported shapes remain investigable, not automatically inferred.

The candidate query joins current Stripe projected checkout attempts to their named applied settlement receipts, restricts the original account/configuration, and finds at most two distinct original deposit IDs whose Session/PaymentIntent/Charge plaintext reference hints intersect the signed facts. Two candidate originals are ambiguous and refused. A single plaintext candidate is NOT trusted: the original's wallet/player/deposit/payment/attempt terms, authenticated original capture receipt, permanent identity ownership, confirmed canonical net credit and source/currency/mode/reference continuity must all pass existing review proof. Contradictory signed Charge/PaymentIntent references cannot be forced onto the first match.

Discovery occurs outside the write root. For a candidate, routing acquires original wallet → player → deposit → payment → attempt locks before the inbox row. It then re-reads/revalidates source custody and repeats candidate discovery inside that SQL root. Changed discovery refuses `stripe_routing_stale`; it never switches to a different wallet after holding an inbox lock. Without a candidate, only the inbox row is locked, and a newly visible candidate similarly requires a fresh top-level retry. Existing review entry points still reject caller transactions. The explicit `inspectInOriginalTransaction` coordinator requires an existing SQL root, re-acquires/proves original ordered locks itself, checks current staff and uses its own savepoint; it never accepts a caller-provided capture/case/credit proof. A caught inner failure cannot publish a partial case in a committing caller.

A routed decision requires the particular signed inbox row to have become an authenticated observation of that exact original's review case in the same transaction. Failure writing or validating routing custody rolls back this transaction's case/observation/decision changes, not the independently committed original signed inbox. Existing prior case/history commits remain unchanged.

## Append-only routing custody

`stripe_followup_route_decisions` records `routed` or `unmatched` decisions with an authenticated encrypted receipt and SHA-256 digest. The receipt binds inbox/event identity, account/configuration, signed source/body hashes, discovered deposit, case UUID/version/evidence hash and original recording actor. A unique decision key derives from the bound outcome facts, not from a staff-supplied target or amount. No raw payload, secret or customer data is included in UI/history summaries.

A duplicate same-outcome route re-proves the current original/review and validates ALL available routing history before returning the existing decision. It does not re-encrypt that receipt or pretend the replaying operator was its original author. Another currently authorized staff member may replay an observational route; the summary preserves the actual recording actor. This differs deliberately from exact actor/note identity required for an acknowledgement.

An initial unmatched decision can be followed by a routed decision after capture evidence becomes visible. Old unmatched receipts remain unchanged. Once routed, the same signed source cannot be downgraded to unmatched, reassigned to another deposit/case, moved behind an earlier case version, or given a different hash for the same version. Existing receipts are validated against both their ciphertext/digest and the source/index fields. Missing/corrupt available custody refuses routing/history. There is no external append-only witness or new independently signed global history manifest: deleting an entire routing history through a privileged raw database path is not falsely certified detectable by this table alone. Domain/model/UI paths provide no such deletion capability.

At most100 routing decisions per inbox row are supported. The query reads at most101; overflow refuses, and an exact existing replay at100 remains valid. A new outcome at capacity refuses the whole route root. Existing Part56 limits also apply: at most5000 current account/configuration inbox rows per review scan and100 observations per case. Saturation is a held incident requiring an explicit reviewed archive/partition/migration plan, not silent pagination of supposedly complete evidence.

## Meaning of UI states

- **Not routed:** no routing decision is currently indexed for this source. It does not imply the event was never inspected through the original deposit UI.
- **Unmatched:** no supported applied original candidate was found in that routing SQL snapshot. The signed event remains retained and investigable. It is not an authenticated provider negative, resolution, harmless event, refund absence proof or authorization to release/resend.
- **Routed:** an authenticated original and particular case observation/version were proved at that routing transaction. It is not an acknowledgement, current risk clearance, financial resolution or live remote finality.
- **Last routing hint / discovered deposit / last observed case version:** list columns read historical indexes for triage. They are not authenticated current case-clearance labels. Use authenticated history and fresh routing/deposit inspection for proof; never use table hints to authorize a payout.
- **Held:** a batch item refused its scope, proof, ambiguity, capacity or configuration boundary; no new decision is manufactured for that failed item.

The global queue does not persist an increasing-ID consumption cursor. Older IDs remain queryable/filterable and can be explicitly routed after a higher ID was handled. UI pagination is navigation, not a durable consumer checkpoint or complete-ingress certificate. The lower-ID test publishes controlled fixture custody out of order; it is not a true uncommitted-writer/crash experiment.

## Scope and non-authorities

There is no automatic router, scheduler, background sweep, automatic header reopening on arrival, provider HTTP call, new credit, debit, journal, balance/status mutation, refund submission, reversal, dispute response, acknowledgement, withdrawal block or risk clearance in this service. New linked evidence is observed when explicit routing/review runs and then reopens the existing review version under Part56 rules. Signed inbox arrival itself remains independent of the wallet lock; no global ingress/review fence or unknown/future-event absence claim is made. There is no automatic account/key migration or cross-provider/Connect/thin-event support.

Native acceptance separately exercises two simultaneous wallet-waiting routes, two simultaneous inbox-waiting unmatched routes, and a route versus stale acknowledgement under a genuine shared wallet wait. Each witness must identify two distinct child database connections blocked by the parent. These certify the named original/source roots and do not certify every global writer, permission cache invalidator, native ingress duplicate, cross-account identity race, OS-kill/power-loss or production deployment. See the delivered exact acceptance JSON and runtime logs; synthetic/local verification is not live Stripe merchant certification.

Retained official protocol references from Part56: https://docs.stripe.com/webhooks , https://docs.stripe.com/webhooks/signature , https://docs.stripe.com/api/events/types . This part makes no live API request and does not change the signed-ingress protocol.
