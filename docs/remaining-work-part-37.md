# Part37 — original withdrawal debit and non-expiring reservation ownership

Date: 2026-10-16. Continuation starts File650. This tranche changes real application services, the SQL schema and original Payment callers; it is not a test-only delivery. This document supersedes Part36's scope list only where explicitly stated below. No live transfer, production rollout, provider/merchant acceptance or universal legal approval is implied.

## Implemented application changes

1. `withdrawal_reservations` permanently identifies one approval reservation per withdrawal: original wallet, beneficiary user, currency, exact gross amount and SHA-256 terms fingerprint. States are active, consumed or released. The consumed row identifies its unique canonical financial transaction. There is no expiry, takeover, reset, deletion, inferred historical owner or automatic backfill. Foreign keys restrict physical parent deletion, and rollback refuses a nonempty ownership table.
2. New withdrawal requests replace any supplied original-terms hash with a server-computed hash of reference, owner, wallet, currency, gross, fee, net, method, encrypted-destination contents and merchant-account label. Approval checks the snapshot and creates the wallet hold and its durable owner atomically. Later covered callers verify the approval's independent durable fingerprint as well as any request snapshot. Mutable status/metadata cannot by itself invent an owned hold.
3. Consumption/release requires this withdrawal's active record, its original terms and enough aggregate locked money for the exact row-wise sum of **all covered active withdrawal owners** in that wallet. A missing record or collective deficit is a refusal even if the individual request's amount fits the wallet aggregate. Neither a forged Approved state nor another withdrawal's live hold substitutes for ownership. Duplicate release cannot release a newer neighbour's hold.
4. Withdrawal completion always derives the economic debit key from the withdrawal ID; caller delivery keys never select or coalesce the debit. Canonical-key collisions, linked-but-unmarked debits and inconsistent terminal rows require controlled review. The former opportunistic healing path is removed. No historical foreign transaction ID can complete the current request.
5. A completed replay, `isSettled`, read-only verification and original-withdrawal browser Paid projection require the original canonical Completed Withdrawal transaction, exact gross/fee, wallet/user/currency/reference mapping, two balanced journal entries on the proper currency-specific player-liability and withdrawal-clearing accounts, the player's debit wallet link, a consumed durable owner linked to that transaction, the original completion timestamp and the original withdrawal transaction pointer. Missing/deleted/wrong-side evidence is never reconstructed.
6. Known provider references must already have compatible local, outbound and global financial owners for terminal proof. Replay does not call bind to manufacture missing historical evidence. New binding remains atomic and checks existing ownership across covered original Payment/prize/deposit/withdrawal lanes. A contradictory or soft-deleted Payment cannot justify finality. Existing Payment facts must agree and be Captured before new settlement; webhook, normalized callback, dispatch acknowledgement and maker/checker completion now coordinate that update in the same transaction.
7. Normalized withdrawal callbacks use a dedicated wallet-first application boundary: wallet -> withdrawal -> original Payment -> reference owners -> accounting. It checks the original gross, fee, method, user, currency, reference and Payment lifecycle, refuses Pending unapproved withdrawals, verifies real terminal proof on replay and refuses a reversal word instead of manufacturing a Refunded marker. Verified definitive failure releases the original owned hold once and repeats observe its released record. DTO construction alone does not authenticate a sender; only already-verified envelope callers may invoke this internal service.
8. Dispatch checks original terms and owned active reservation before any external invocation. Unknown/outbound claims prevent ordinary cancellation, rejection or manual failure from releasing the reservation. Only internal already-verified final-nonacceptance adapter/webhook/callback or independent maker/checker callers set the explicit failure-release capability. It is not forwarded from request options. Existing uncertain dispatches are neither resent nor reset. Identity detention does not erase ownership: a safe permitted cancellation can release the owned hold even when the status no longer says Approved.
9. Request, approval and completion own SQL savepoints even inside ambient transactions. A caller catching a domain refusal cannot commit the service's half-consumed hold, new reference owner or partial reservation write. Unlock-before-debit preserves the wallet database invariant, and both halves commit or roll back together.

## Compatibility and deployment boundary

- Apply the additive migration only under an authorized tested rollout. No production migration or historical wallet mutation was executed here. Drain/pause competing money-out writers and inspect balances/reservations before enabling the new code across all workers; do not mix old and new completion code against live obligations.
- Existing Approved/Processing/Completed withdrawals without durable ownership cannot be consumed, released, replay-proved or upgraded automatically. Retain any uncertain funds; inventory and reconcile originals through an authorized independent historical procedure. Do not insert guessed owners merely to make the guard pass. Earlier custom/callback-key debits are not silently rekeyed. Missing original evidence stays a controlled-review exception, not a healed success.
- Historical unapproved requests may still pass explicit existing approval review of their current terms and create a new owned reservation. This establishes the approval's current original terms, **not** a reconstruction or authentication of an unavailable earlier request snapshot. New requests pin the request snapshot as well. Review such historical intake before rollout.
- Local/manual accounting completion with **no Payment and no known provider reference** remains supported. It is not evidence of authenticated bank delivery. Known reference ownership is never fabricated or inferred for that lane. Configuring a merchant reference or uploading human evidence does not authenticate a provider or authorize a live transfer.
- The ownership protection covers the coordinated original withdrawal approval, processing, completion, rejection, cancellation, final-failure, dispatch, webhook, callback and maker/checker lanes. It does not retroactively make generic wallet holds, generic expiring WalletReservation/FinancialHold records, arbitrary direct SQL or unmanaged legacy balance/hold writers obligation-aware. A deployment must isolate those writers and audit all outstanding non-withdrawal liabilities too. No claim of a database-wide hold conservation proof is made.
- Snapshot fingerprints are integrity checks against covered mutation, not signatures against a malicious database administrator. Database credentials, least privilege, backups, immutability policy and operator authority remain deployment responsibilities. The original payout details remain encrypted/hidden; no destination plaintext or customer data is packaged.
- Per-wallet exact active-owner scans and original historical reference scans have not been certified at deployment volume. The Part36 financial reports remain observational across multiple queries; they do not become an atomic accounting snapshot or authority to repair/release funds through this change.
- Existing maker/checker permissions, current independent authority, encrypted evidence, country/provider/KYC/AML and finance-engine gates remain. Internal PHP service callers are trusted code boundaries; they must never be exposed as unrestricted request options or used to bypass route/job authorization.
