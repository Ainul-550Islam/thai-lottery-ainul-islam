## Actual application work

1. **Exact original credit, not a status or foreign key.** Completion re-queries persisted data under wallet → deposit → original Payment locks. Active original owner, original wallet/currency, positive gross and net, nonnegative fee, and exact `gross − fee = net` are required. Newly requested deposits carry a server-assigned original-terms hash and a non-secret receiving-account label; caller metadata cannot replace those generated values. A stale input model does not select the current facts. Existing request-key replay revalidates those original terms and account.
2. **One canonical transaction and real ledger proof.** Only the deterministic deposit credit key is accepted; arbitrary caller keys are refused. A credit must be the original Completed Deposit transaction with the same owner, wallet, deposit reference, currency and exact net amount. Exactly two nondeleted balanced postings must have the correct currency-specific system-cash debit and player-liability credit, exact net, and original liability wallet. Existing caller description, actor and event/operator transaction metadata survive, while original canonical deposit fields override conflicting caller metadata. A foreign financial-transaction FK, missing transaction, duplicate/corrupt journal or contradictory existing canonical history is not permission to credit, replay or automatically repair.
3. **Durable original reference ownership.** The new `financial_provider_reference_owners` table owns a canonical provider/account/reference identity across covered deposit, withdrawal and external-prize paths. It stores hashed reference/facts rather than the raw provider reference. The existing local/outbound indexes remain and are checked. Unique obligation/Payment ownership, exactly one obligation FK, restrictive deletes, exclusive no-op upsert and savepoint-atomic refusal prevent stealing or partially committing a competing owner. A previously null original Payment attachment may be assigned once; an existing nonnull association cannot be reassigned through these services. No expiry/reset/takeover/release route exists.
4. **Conservative cross-direction holds.** In the absence of an approved provider-specific namespace contract, identical provider/account/reference across incoming and outgoing obligations is refused. This is a deliberately conservative application policy, not a claim that every actual provider shares inbound/outbound namespaces. Legitimate references may therefore be held. Existing Payment gateway/reference uniqueness is broader than account scope and remains conservative. Known local indexes, historical Payment rows, original deposit/provider references, withdrawal dispatch/reconciliation and external-prize metadata include soft-deleted history in refusal checks. Unknown historical account context stays `legacy-primary`, never the current account by inference.
5. **Account rotation does not rewrite history.** `payment.deposit_reference_accounts` is an operator-controlled map of stable non-secret labels; `metadata.inbound_provider_account` records the request label. Labels are bounded and validated. Reusing a label for a different receiving account is prohibited operationally. Changing the active label holds old work; it does not silently remap a reference or authorize another arrival. No account credential, country approval or universal provider authentication is encoded by a label.
6. **Both inbound callback callers use original evidence.** The classic verified-webhook binding validates original terms and exact gross/fee/owner/method/provider/currency/reference facts before reservation. Created Payments attach to the original owner inside the same transaction. Success uses canonical completion; late failure cannot downgrade a proved credited deposit. Failed, cancelled, disputed, partially refunded or otherwise incompatible original Payments do not become fresh payable credit opportunities. Existing classic reversal processing now verifies original canonical credit before reversing its original transaction; this does not send a refund or invent a provider reversal protocol.
7. **Normalized callback integration is atomic.** The normalized callback resolves exactly one nondeleted original Payment including provider aliases and deleted history. A new helper owns wallet/deposit/Payment locks and validates original money facts; verified success may approve Pending, capture the original Payment, and canonically credit in one transaction. Only Pending/Authorized originals may newly settle. A Reversed word is refused: it is not by itself an authorized original-transaction reversal. Non-success words do not credit; terminal successful replays prove the existing original settlement and never repair it. These are internal domain callers of already authenticated envelopes, not authentication mechanisms themselves.
8. **Browser success is private and proved.** Browser return requires an authenticated matching owner. Captured alone no longer means paid: read-only `verifySettled()` must establish original transaction, ledger and immutable owner. Invalid historical data is withheld as pending/unpaid, with no browser-triggered binding, repair or credit. The existing admin `isSettled()` field remains a state/FK diagnostic, not independent provider arrival proof; use the audit command for canonical local accounting proof.
9. **Manual matching cannot reroute a document.** A supplied internal deposit document must uniquely match that original nondeleted row. It cannot fall back to another deposit by provider reference. Reference-only ambiguity including deleted rows is refused. Terminal manual verification proves actual original settlement. Manual claim amounts retain the existing net-credit contract; authenticated provider callback amounts are exact original gross. Manual matching is an internal operator service, not provider authentication or an exposed player self-credit endpoint.
10. **Usable authorized admin and operator checks.** Admin completion requires the independently checked original provider/statement reference, preserving a previously pinned value. All four deposit decision closures independently recheck current active panel access and money-management permission before delegation; hiding a button is not the only check. A typed reference is explicitly not provider authentication. The new `payments:deposit-reference-audit` command requires exactly one selector or a bounded oldest-200 scan and emits only redacted IDs/status/proof categories. It performs no binding, credit, backfill, provider call or historical repair. A held record remains held even though a successful diagnostic invocation can return exit0; inspect each `proof` value.
11. **Existing expiry/history integration is retained.** New global ownership also protects covered prize-claim/legacy-disbursement annotation writers from resetting financially managed obligations. Withdrawal audit selects the original wallet ID needed by the immutable facts fingerprint. No unknown outcome becomes permission to release funds or resend.
