# Part39 — original-bound compensation and truthful refund boundaries

Date: 2026-10-16. Continuation begins File691. This tranche fixes application services, not only tests. Part38 remains authoritative except for the explicit changes below. Local accounting compensation is not external refund delivery or authorization to operate in any country.

## Implemented application fixes

1. `FinancialReversalService` no longer trusts a caller model's status, wallet, amount, currency or metadata. It uses only its persisted ID, obtains a persisted routing hint before starting an owned transaction, locks the real wallet **before** the original header, and rejects changed ownership. Routing outside the owned transaction avoids establishing a needless MariaDB repeatable-read snapshot before waiting for that wallet. Inside a caller's ambient transaction, the caller's own snapshot/rollback responsibility remains; the service never retries that outer transaction from a savepoint.
2. `ReversalIntegrityGuard` checks the original header, positive full amount, zero fee, processing stamp, engine/storage-type agreement, beneficiary, wallet and currency, nondeleted posted entries, account currency, exact debit/credit totals and canonical account/direction. A wallet movement needs precisely one full-amount player-liability leg and its correct counterpart. This is stricter than a balanced-journal or Completed-label check. Nonzero fees require a domain-specific policy rather than silently assuming that fees are refundable.
3. Existing primitive postings inherit the original wallet ID onto the counterparty entry as context. The guard accepts that known representation **only for the same wallet and correct canonical counterparty**; it does not mistake that entry for the wallet leg. Direction and the wallet balance snapshot are derived from the liability account, not the first matching wallet_id or row order. Original entries are never rewritten by application reversal. Explicitly walletless standalone adjustment/settlement journals can be mirrored without touching a wallet; stripping a wallet from a player-money header is refused.
4. The sole accepted reversal key is deterministically derived from the original ID. A supplied different key, another original's key, foreign result reference, soft-deleted result, partial result, duplicate candidate or contradictory original lifecycle fails closed. Candidate and entry reads inside transactions are locking/current reads, including old ambient InnoDB snapshots. No unknown claim is reset, adopted, resent or automatically repaired.
5. Valid replay is supported **after** the original becomes Reversed: the service proves the single Completed compensating header, original-bound metadata, stable original/entry fingerprint and exact one-to-one opposite entries. Replay is read-only, works after later wallet activity or a later freeze, and does not re-credit, re-debit, change reason/actor or rewrite original accounting. `existingReversalFor` now returns only proved compensation, not the first unvalidated matching row. `canReverse` is explicitly advisory; the authoritative checks repeat under locks.
6. New compensation respects current wallet debit/credit eligibility and available balance, while preserving Part38's withdrawal hold floor. Header claim, wallet mutation, mirrored journal, final proof and original Reversed stamps share one SQL transaction/savepoint. Failures after wallet mutation or even after all mirror entries are posted roll back the whole compensation when an outer caller catches the error. Top-level SQL deadlock retry is bounded; no inner retry pretends to reconstruct a database-aborted outer transaction.
7. Generic compensation refuses known managed Deposit, Withdrawal, Payout, WalletConversion and Bet polymorphic originals. Durable Deposit/Withdrawal/Payout/WalletConversion transaction links also prevent bypass by removing their type label. This is **not** a claim of universal ownership discovery for every legacy domain. These obligations need their own proved coordinated domain workflow; their Confirmed/Completed/Paid label must not be left contradictory by a generic wallet/journal operation.
8. `ExternalRefundPolicy` explicitly records the absent provider/merchant refund, incoming-fee and dispute policy. Legacy `RefundService` cannot use a human reason, caller actor ID, Refunded label or arbitrary financial_transaction_id to fabricate a successful refund/replay. Normalized refund/chargeback webhooks return a failure instead of changing settled deposits, recrediting completed withdrawals or reporting a local credit as external delivery. Even a correctly signed synthetic Stripe event does not supply a refund-specific merchant policy or prove bank delivery. No caller boolean/config switch bypasses this refusal. This legacy capability is intentionally isolated, **not implemented as a live provider refund adapter**.
9. Legitimate agent paid-commission reversal remains functional through its domain caller. Both bet and draw paths now require that commission's own correct type/reference, agent beneficiary, amount, currency and reversible original proof. Missing/foreign/unprovable links throw before commission labels and agent aggregates are changed; they are no longer silently skipped while bookkeeping says Reversed. Broader aggregate-concurrency/historical-bookkeeping acceptance is not thereby certified.

## Native snapshot and mutation-control interpretation

Each dedicated new race starts two independent child connections, gates both behind the parent's actual wallet lock and records simultaneous direct-parent InnoDB waits. The five profiles exercise duplicate original replay, distinct identical-economics originals, cross-original key collision, competition for the last available money and old snapshots predating a newly committed compensation. In the old-snapshot profile both children first record zero reversal rows; the parent posts the one compensation under its owned lock, verifies both waiting children and commits, after which both children must return the same proved canonical result.

MariaDB 11.8's snapshot-conflict mode can safely abort an old-snapshot lock before the application reaches its current-read proof. Only the explicitly selected synthetic snapshot child/session temporarily disables that optional mode, preserving and restoring its prior value in finally. No global mode, production setting, constraint or application isolation weakening is made. Ordinary owned-transaction races keep native defaults. During development, plain routing inside the new owned transaction unnecessarily established a read view and caused native error1020 for a waiting contender; the final wallet-first implementation reads its route outside that owned boundary. Ambient snapshot conflicts still fail closed and require the owning caller to retry its whole operation.

A separately labelled negative control temporarily removes only the reversal-candidate locking read and runs the old-snapshot regression. Its expected failure is a refusal of a **valid replay**, not a double-money success: other safety guards still prevent a new compensation. The correct source is restored byte-for-byte in finally, and normal focused native acceptance is rerun after restoration. No mutant source is shipped. This control proves candidate visibility, not deployment-scale concurrency or bank authentication.
